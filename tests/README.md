# 验收测试

三个脚本，**只用 Python 标准库**，不需要 pytest、不需要装任何东西。
用途是：改完代码 / 换完数据库，先跑一遍，确认没有哪条链路被改断。

```bash
python tests/smoke.py          # 28 个接口是否都返回 200
python tests/acceptance.py     # 权限、金额、编码、关联是否正确
python tests/agent_contract.py # 智能体的护栏（确认摘要、查无此人）
```

另有一个**不查对错、只量成本**的探针（会真花几厘钱，所以不进 CI）：

```bash
cd agent-server && ./.venv/Scripts/python.exe ../tests/usage_probe.py --rows 20
```

## 各脚本的分工

| 脚本 | 回答的问题 | 判据 |
|---|---|---|
| `smoke.py` | 接口**通不通** | 28 个接口全部 200 |
| `acceptance.py` | 行为**对不对** | 18 条断言，见下 |
| `agent_contract.py` | 智能体**会不会乱来** | 11 条断言，见下 |
| `usage_probe.py` | 一次问答**花多少钱** | 只报数，不判定 |

`smoke.py` 只做状态码检查——它故意不判断数据，因为数据正确性需要上下文（谁是普通销售、金额该是多少），那是 `acceptance.py` 的活。

## acceptance.py 验什么

**① 行级数据隔离** —— 这是 RBAC 系统最容易做错、也最容易糊弄过去的地方

- `admin` 能查全部客户
- `user001`（普通销售）查全部 → 必须 403
- `zhengping`（无客户权限）→ 必须 403
- `user001` 查「我的客户」→ 200，且条数是全部的真子集（不是"能查但查的是全部"）

**② 金额精度** —— 这类系统的头号敌人

- 扫描 7 个含金额的接口，**响应里不能出现任何一个 float**
- 所有 `*_amount` 字段必须是 `^\d+\.\d{2}$` 形式的字符串

判断依据：只要 JSON 里出现 `2200.0` 这种值，就说明 `Decimal → float` 在某一层被转换了，精度已经不可靠。

**③ 中文编码** —— 曾经踩过坑，这条是防复发

- 客户姓名不含 `U+FFFD`（替换字符）和 `?`
- 列表与详情返回同一个人的姓名一致

**④ 关联与金额计算**

- 没有孤儿订单 / 孤儿跟踪记录（每条的 `customer` 都能解析出 id）
- **订单金额 = 明细「数量 × 单价」之和**，用 `Decimal` 精确比较，不留容差

**⑤ 客户消费统计一致性**

- 每个客户的 `order_count` / `order_amount` 必须等于其订单的真实笔数与金额合计

这条盯的是反范式冗余字段有没有悄悄漂掉。后端的维护方式是"按订单表重算"
（`backend/system/utils/customer_stats.py`），不是 `+1/-1` —— 因为删单不走模型方法、
改单会换客户、直接改库完全绕过接口，增量维护只要漏一次就永久偏，而且不报错。

数据已经漂了可以用 `python manage.py sync_customer_stats --dry-run` 体检。

**⑥ 非法输入拦截**

- 提交非法支付方式（如 `"微信"`），必须返回 **400**，不能是 500

`sale_order.pay_way` 在库里是 `enum('wxpay','alipay','bank','cash')`，模型如果只写
`CharField` 而不声明 `choices`，任意字符串会一路走到 MySQL 才炸成
`Data truncated for column 'pay_way'` —— 一个本该 400 的输入错误被伪装成服务端故障。

## agent_contract.py 验什么

这个脚本**不调模型**。模型输出不稳定，但"写操作前的确认卡里显示什么"必须是确定的——
所以这部分归代码管，能被 CI 覆盖；提示词层面的"不许编造"只能人工抽查。

**① 确认摘要必须来自真实数据**

模型只被允许给出 `customer_id`。摘要里的客户名、客户等级、归属销售，全部由
`crm/tools.py::describe_add_tracking()` 现查接口填进去：

- 客户字段必须带 `ID=1`（人看名字，系统看 ID，两者都要有）
- **摘要里的客户名 == `GET /api/customer/1/` 返回的 name**
- 带归属销售、带"确认后立即写入数据库"这类后果说明

第三条是重点：如果哪天有人把摘要改成"让模型自己总结"，这条断言会立刻红。
模型把「韩楚风」写成「韩总」、把 3200 写成 32000，都是真实发生过的失败模式。

**② 客户不存在时给警告，而不是照抄参数**

传 `customer_id=99999999`，接口 404，此时摘要必须：

- 带 `警告` 字段（"客户详情读取失败，HTTP 404，请先核对"）
- 仍然回显传入的 ID（不是留空——留空人就没法核对自己填了什么）

**③ 查不到人时，工具明确返回命中 0**

搜一个不存在的名字，工具要返回 `ok=True` + `命中数=0` + 提示语。
不能报错（报错模型会理解成"系统坏了"而不是"没这个人"），也不能悄悄返回全表
（那模型会拿别人的数据顶上去）。

## usage_probe.py 量什么

这是**测量**，不是断言。跑一次真花几厘钱，结果也依赖厂商当天的缓存行为，所以不进 CI。

它用真实的工具说明书（直接读 `crm/tools.py` 的 `TOOLS`）和真实系统提示词，
只把工具执行结果换成可控假数据 —— 所以量出来的输入 token 和线上一致。

实测一次「帮我查全部客户，列出前几个」：

| 列表返回 | 请求次数 | 输入 token | 输出 token | 第 2 次请求 |
|---|---|---|---|---|
| 20 条 | 2 | 3652 | 975 | 2598 |
| 5 条 | 2 | 2536 | 317 | 1482 |

两处值得注意：

- **输出那一列降了 67.5%**。工具返回 20 条时，模型会把 20 条全复述进答案。
  所以列表条数是**在输入和输出两边同时收费**的。
- **第 2 次请求是第 1 次的 2.46 倍**。这就是"历史只增不减"的代价：
  同一轮问答里，工具结果原样塞回上下文，下一次请求要连它一起重发。

```bash
cd agent-server
./.venv/Scripts/python.exe ../tests/usage_probe.py              # 默认 20 条
./.venv/Scripts/python.exe ../tests/usage_probe.py --rows 5     # 看收窄能省多少
```

用 **agent-server 的 venv**（backend 里没装 `openai`）。

## 目标与密码从哪来

```bash
# 默认打本机 8000
python tests/acceptance.py

# 换地址 / 换密码（环境变量优先）
DJRBAC_BASE=http://127.0.0.1:8001 DJRBAC_PASSWORD=xxxx python tests/acceptance.py
```

密码解析顺序：`DJRBAC_PASSWORD` 环境变量 → `agent-server/.env` → `backend/.env`。
仓库里不存密码，所以本地跑之前要先把 `.env` 配好（见根目录 README）。

## 退出码

| 码 | 含义 |
|---|---|
| 0 | 全部通过 |
| 1 | 有断言失败（会列出失败项） |
| 2 | 前置条件不满足：连不上后端 / 密码不对 / 找不到密码 |

失败时退出码非 0，可以直接挂进 CI 或一键启动脚本。

> 顺带说明：`smoke.py` 里有一项 `?name=张三` 的模糊查询。
> Django 查询结果为空时不会真正执行 SQL，所以这个接口在数据层坏掉时**也可能返回 200**。
> 想验数据层，看 `acceptance.py` 的金额与关联断言，别只看状态码。
