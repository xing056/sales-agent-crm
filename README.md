# sales-agent-crm

> 把 LLM 智能体嵌进一套真实的 RBAC 后台管理系统：**智能体用当前登录人的身份查数据、办事情，受同一套权限约束。**

Django 5.2 · DRF · Vue 3 · Element Plus · MySQL 8 · 手写 Agent Loop（不依赖 LangChain）

---

## 这不是"又一个聊天框"

大部分智能体 demo 长这样：一个对话框，背后连着一个玩具数据库，问什么答什么，权限、身份、上下文全都不存在。

大部分后台管理系统长这样：表单、表格、下拉框，查一个客户的订单要点三次。

这个项目把两件事接在一起 —— 智能体就长在后台管理里，**右下角一个悬浮球**，你说的每一句话都在真实业务数据上执行：

| 你做什么 | 它怎么反应 |
|---|---|
| 停在「客户详情」页，问「**这个客户**有哪些订单？」 | 它知道你在看 ID=1 的客户，直接查，不反问你 |
| 用 `admin` 登录问「这个月销售额多少」 | 用你的 JWT 调接口，返回真实统计数字 |
| 用 `user001`（普通销售）问「查一下全部客户」 | 后端返回 403，它**如实说没权限**，并建议改查「我的客户」 |
| 说「给韩楚风记一条跟踪，下周回访」 | 弹出确认框，你点「执行」才写库 |
| 问「我们的退货政策是什么」 | 说明系统里没有这项信息，**不编造** |

## 四个关键设计

### 1. 智能体继承人的身份，不新建账号体系

前端把 Pinia 里的 `accessToken` 直接递给智能体，智能体拿它去调业务接口。
于是 RBAC 和行级隔离**自动生效** —— 不需要在智能体里重写一遍权限逻辑，也不会出现"智能体能查到、人查不到"的越权口子。

```
用户登录 → JWT → 智能体工具的每一次请求都带同一个 JWT → 后端照常鉴权
```

### 2. 页面上下文注入：让"这个客户"有指代

智能体知道你在哪个模块、正在看哪条记录。做法朴素但有效 —— 拼进系统提示词：

```
当前界面上下文：用户正停留在「客户详情」页面。
用户当前打开的是客户 ID=1 的详情页。用户说「这个客户」时，指的就是 ID=1；
可直接用 get_customer / get_order 按这个 ID 查询，不必再反问。
```

独立对话框做不到这件事，只有长在业务系统里才行 —— 这也是把它嵌进后台的意义。

### 3. 工具可插拔：换一套工具 = 换一个业务场景

`agent/core.py` 的循环不认识任何业务，它只认三个模块级变量：

```python
core.TOOLS            # 给模型看的工具说明书（JSON Schema）
core.TOOL_DISPATCH    # 工具名 → 真实执行函数
core.CONFIRM_REQUIRED # 哪些算危险操作，执行前要人工确认
```

`bridge.py` 启动时把 CRM 的这三样注入进去，循环一行不用改。
想接别的系统，照 `crm/tools.py` 写一份自己的三件套即可。

### 4. 金额全链路不碰 float

财务字段一旦过 `float` 就会在第四位小数上开始漂。这个项目在四层都做了处理：

| 层 | 做法 |
|---|---|
| 数据库 | `decimal(10,2)` |
| Django 模型 | `DecimalField` |
| 业务计算 | `Decimal` 运算，`ROUND_HALF_UP` |
| JSON 输出 | 自定义 `MoneySafeJSONRenderer`，Decimal 输出为**字符串**而非浮点 |
| 前端 | `BigInt` 按"分"计算与格式化，全程不走 `Number()` |

自带审计脚本可复查：`python agent-server/money_audit.py`（扫描 17 个接口的金额字段，输出 0 float 即通过）。

## 快速开始

### 前置

- Python 3.11+
- Node.js 20.19+ / 22.12+
- MySQL 8.0+

### 1. 准备数据库

```bash
mysql -uroot -p -e "CREATE DATABASE dj_rbac DEFAULT CHARSET utf8mb4;"
mysql -uroot -p --default-character-set=utf8mb4 dj_rbac < backend/sql/seed.sql
```

种子数据：17 张表、91 个权限码、10 个角色、22 个用户、107 个客户、12 笔订单、7 条跟踪记录。

> 导入时务必带 `--default-character-set=utf8mb4`，否则 Windows 下的 mysql 客户端会把 UTF-8 当 GBK 读，中文全部变乱码且不可逆。

### 2. 后端

```bash
cd backend
cp .env.example .env          # 改 DB_PASSWORD 为自己的密码
python -m venv .venv && .venv\Scripts\activate     # Windows
pip install -r requirements.txt
python manage.py runserver 8000
```

接口文档：http://127.0.0.1:8000/api/schema/swagger-ui/

### 3. 智能体服务

```bash
cd agent-server
cp .env.example .env          # 填 LLM_API_KEY / LLM_BASE_URL / LLM_MODEL
pip install -r requirements.txt
python server.py
```

任何 OpenAI 兼容端点都能用（智谱 / 百炼 / DeepSeek / 本地 vLLM）。

日常使用走后台管理页面里的悬浮球，**智能体会带上前端已登录的 JWT**，不需要额外配置。
独立调试页 http://127.0.0.1:8200/ 是另一条路：它靠"选账号 + 统一密码"登录，属于本机演示便利，
默认关闭。要用的话在 `.env` 里加 `AGENT_ALLOW_USER_LOGIN=true` 并填好 `DJRBAC_PASSWORD`
（开启后，任何能访问到 8200 的人都能只凭账号名以该身份查数据，仅限断网本机演示）。

### 4. 前端

```bash
cd frontend
npm install
npm run dev
```

打开 http://127.0.0.1:5173/ ，用 `admin` / `123123` 登录，点右下角悬浮球。

### 或者一键启动（Windows）

```
双击 启动演示.bat
```

三个服务分别在独立窗口启动，并自动打开后台管理页面。

## 智能体的 9 个工具

| 工具 | 作用 | 需要确认 |
|---|---|---|
| `whoami` | 当前登录人是谁、什么角色 | |
| `list_customers` | 按条件查客户（姓名/等级/状态） | |
| `my_customers` | 只查本人的客户 | |
| `get_customer` | 查单个客户详情 | |
| `list_orders` | 查订单列表（可按客户过滤） | |
| `get_order` | 查订单详情（含明细行） | |
| `list_trackings` | 查客户跟踪记录 | |
| `sales_stats` | 销售统计（月度/年度/业绩排名） | |
| `add_tracking` | 写一条跟踪记录 | ★ 弹确认框 |

工具内部一律走 REST 接口、带用户 JWT，**没有一条 SQL 直连数据库**。
工具抛异常会被兜底成一条"工具结果"回灌给模型，让它自己纠错重试，而不是整个循环崩掉。

## 数据一致性：客户消费统计怎么维护

`customer.order_count` / `order_amount` 是反范式冗余字段（客户列表要按消费额排序、筛选，实时 join 太贵）。
关键在于**怎么维护**——不是下单 `+1`、删单 `-1`，而是**按订单表重算**：

```python
# backend/system/utils/customer_stats.py —— 建单 / 改单 / 删单之后调用
sync_customer_stats(customer_id)
```

为什么不用增量：删单走 `queryset.delete()` 不触发模型方法、改单把客户从 A 换到 B 只更新一边、
直接改库完全绕过接口 —— 任何一次漏掉，误差就永久留在数据里，**而且不报错**，只能靠对账发现。
重算是幂等的，跑一次和跑十次结果一样，即使数据已经漂了也能修回来。

历史数据、或有人绕过接口改了库，用命令修：

```bash
cd backend
python manage.py sync_customer_stats --dry-run   # 体检：列出对不上的客户，不写库
python manage.py sync_customer_stats             # 修正
```

这条链路由 `tests/acceptance.py` 的第 ⑤ 组断言盯着（每个客户的统计必须等于其订单实际），
不依赖任何人记得去手动跑命令。

## 验收测试

三个脚本，**纯标准库**，不用装 pytest：

```bash
python tests/smoke.py          # 28 个接口是否都返回 200
python tests/acceptance.py     # 权限隔离 / 金额精度 / 中文编码 / 关联完整性
python tests/agent_contract.py # 智能体护栏：确认摘要、缺失客户、查无此人
```

`acceptance.py` 的 18 条断言里，最值得看的三条：

- **行级隔离**：`user001` 查全部客户必须 403、查「我的客户」必须 200 且条数是全部的真子集 —— 防的是"能查但查的是全部"这种假隔离
- **金额精度**：扫描 7 个含金额的接口，**响应里出现任何一个 float 就算失败**；并校验订单金额 = 明细「数量 × 单价」之和，用 `Decimal` 精确比较不留容差
- **统计一致性**：每个客户的消费次数/金额必须等于其订单实际 —— 防的是聚合字段悄悄漂掉

`agent_contract.py` 是另一类断言：**不调模型**，只验"护栏"——确认框里的客户名必须等于接口返回的名字
（不是模型编的）、客户不存在时要给警告、查不到人时要明确返回命中 0。模型是随机的，护栏不能是随机的。

失败时退出码非 0，可直接挂 CI。详见 [tests/README.md](tests/README.md)。

## 关于界面

后台管理普遍长得一样，这个项目没有追求视觉炫技，只做减法：

- 客户列表 14 列 → 10 列（省市区合并、姓名+手机合并）
- 客户等级用语义标签，而不是裸数字 `1` / `2`
- 金额右对齐、等宽数字，避免对不齐
- 新增「最近跟进」列：超过 30 天未跟进的整行标红（107 个客户里有 103 个从未跟进，数据自己会说话）
- 一键明暗主题：默认**跟随系统**，点一次就记住你的选择，用户菜单里还能切回「跟随系统」
- 全站颜色收敛成 `--app-*` 一套变量，明暗两套值切换，没有逐条 `html.dark .xxx` 的补丁堆

## 安全上的默认值

写的时候按"默认安全、演示可开"来定，逐条都有实测：

| 项 | 默认 | 说明 |
|---|---|---|
| 接口鉴权 | 全部需要登录 | `department` / `stat` / `common` 三个接口原来显式关掉了认证，现在沿用全局 `CustomJwtAuth` + `CustomPermission`；权限类里"未登录"的检查也挪到了最前面 |
| **行级隔离** | 非超管只看自己的 | 客户 / 订单 / 跟踪记录的 `get_queryset()` 按 `user_id` 过滤。之前只有权限码挡着"能不能调接口"，没有挡"能看哪一条"—— 换个 id 就能读到别人的客户和订单（水平越权） |
| **SECRET_KEY** | 占位值拒绝启动 | 默认值写在源码里等于公开。`DEBUG=false` 时若仍用它签 JWT，任何人都能给自己签一个"我是 admin"。现在这种情况直接 `ImproperlyConfigured` |
| **登录限流** | 20 次/分钟/IP | 没有它，登录接口可被字典爆破。`LOGIN_THROTTLE_RATE` 可调 |
| **接口文档** | 跟随 DEBUG | `/api/schema/`、swagger、redoc 原来匿名可读，内容是一份完整接口目录。`DEBUG=false` 时自动不挂载，要开就设 `ENABLE_API_DOCS=true` |
| 智能体身份 | 只认令牌 | 不再接受"只报账号名"就建会话 —— 那等于把一个能读全库的接口开在 8200 上。账号名登录要显式开 `AGENT_ALLOW_USER_LOGIN=true` |
| 跨源 | 白名单回显 | 不在 `AGENT_ALLOWED_ORIGINS` 里的来源拿不到 CORS 响应头，浏览器挡住读取 |
| 图片上传 | 需登录 + 后缀白名单 + 内容校验 + 5MB | 后缀可以随手改，所以额外用 Pillow 真解一遍文件头；落盘目录跟着 `MEDIA_ROOT`，文件名用 uuid |
| 业务响应 | 嵌套只给最小字段 | 客户/订单/提成里嵌的 `user` 用 `UserBriefSerializer`，只回 id、账号、员工姓名 —— 不再把同事的手机、邮箱、角色、部门塞进每一个详情响应 |
| 令牌有效期 | 12 小时 | 原来 7 天且没有黑名单；需要长期免登录请用 refresh_token |
| 会话 | 空闲 30 分钟回收 | 另设 100 个上限，超了按最久未用淘汰；`SESSION_TTL` / `MAX_SESSIONS` 可调 |
| 种子数据 | 手机号已脱敏 | 统一改成 `1380000XXXX` 形式（136 个不同号码），仓库里的 `seed.sql` 与线上库都已同步 |

`DEBUG` 默认 `false`：开着的时候报错页会把堆栈、SQL、局部变量直接吐给访问者。
本机开发想要详细报错页和 debug toolbar，在 `backend/.env` 里写 `DJANGO_DEBUG=true`。
媒体文件（头像、商品图、编辑器上传）走的是 `urls.py` 里显式挂的 `serve` 路由，**与 DEBUG 无关**，
所以关掉调试模式图片照样能看；上生产应当把它们交给 Nginx / 对象存储。

## Token 用量的账本

智能体的成本 = 输入 token × 请求次数 + 输出 token。这个项目把账记下来了，因为
**没有计量就没有优化**：说不清一次问答花多少，后面每一刀省了多少都只能靠感觉。

`agent/core.py` 的每个会话带一本账（`session.usage`），每次请求后读模型的 `usage`
字段累计，并打一行日志：

```
[usage] #1 轮1 输入 1054 输出 12 | 历史 2 条 | 会话累计 in=1054 out=12
[usage] #2 轮2 输入 2598 缓存命中 1664 输出 963 | 历史 4 条 | 会话累计 in=3652 out=975
```

想看某段对话的汇总，`POST /api/usage`（带登录令牌，和 `/api/chat` 同一套校验）：

```json
{"请求次数": 2, "输入token": 3652, "输出token": 975, "缓存命中token": 1664,
 "缓存命中率": "45.6%", "输入增长倍数": 2.46, "当前历史条数": 4}
```

其中 `输入增长倍数` 是最该盯的一个数字：第 2 次请求 ÷ 第 1 次。它 >1 就说明历史在膨胀。

### 实测：一次「查列表」问答的账

用 `tests/usage_probe.py` 量的（真实工具说明书、真实提示词，工具结果用可控假数据）：

| 列表返回条数 | 请求次数 | 输入 token | 输出 token | 第 2 次请求 | 增长倍数 |
|---|---|---|---|---|---|
| 20 条 | 2 | **3652** | **975** | 2598 | 2.46x |
| 5 条 | 2 | **2536** | **317** | 1482 | 1.41x |
| 差 | — | **−30.6%** | **−67.5%** | −43% | — |

这张表里最容易被忽略的是**输出那一列**：返回 20 条时模型的回答是 975 token，
返回 5 条时是 317 token。因为**模型会把工具返回的数据全部复述进答案** ——
工具返回多少，模型就说多少。所以列表的返回条数是**同时在输入和输出两边收费**的，
收窄它等于砍两刀。

### 上下文缓存：已经在工作，但只在段内

模型厂商的上下文缓存是自动的，不需要在代码里"开启"。实测（`glm-4.7`）：

- 同一段对话的第 2 次请求，输入 2598 → 命中 1664（64%），重复几次后能到 2560（98%）
- 但**每段新对话的第 1 次请求（1054 token）永远是全价**，命中 0

所以固定开销（系统提示词 779 字符 + 工具说明书 2869 字符 ≈ 1054 token）
在"每段对话的第一个请求"上必须付全价。想省这一笔，方向是**让会话活得更久**
（少 reset、把会话状态外置到 Redis 而不是内存），而不是去调缓存参数。

### 自己量一遍

cd agent-server
./.venv/Scripts/python.exe ../tests/usage_probe.py              # 默认 20 条
./.venv/Scripts/python.exe ../tests/usage_probe.py --rows 5     # 对比收窄返回

## Tokens 用量看板（超管）

量完之后要能**归到人头上**，否则数字只能自己看。超管菜单「系统管理 → Tokens 用量」
（`/llm-usage`）按账号列出消耗，支持今天 / 本周 / 本月切换，带环比。

### 数据是怎么流过来的

```
agent-server 每次模型请求
      │  core.USAGE_SINK(entry)        ← 核心循环只负责"把账交出去"
      ▼
bridge._report_usage()  ──POST──▶  /api/llm_usage/report/   (X-Internal-Key)
      │                                     │
      │◀──── today_prompt/completion ───────┘  顺手回今日累计，供预算判断
      ▼
                               MySQL  llm_usage（一次请求一行）
                                          │
                                    GROUP BY 查询
                                          ▼
                          /api/llm_usage/summary/?range=...
```

**为什么存"一次请求一行"而不是"每人每天一行"**：只在聚合表里存天/周/月，
等于把口径焊死——哪天"周"的定义改了、或者想追查"这个会话第几轮最贵"，
历史数据就废了。存明细，任何粒度都是查询时算的。

### 三个安全设计

| 项 | 做法 | 为什么 |
|---|---|---|
| 上报接口 | 共享密钥 `X-Internal-Key`，**密钥未配置时拒绝一切请求** | 这是个写接口。走用户令牌的话，任何员工都能给同事伪造账单 |
| 账号归属 | 智能体用令牌调 `/api/user/whoami/` 问"我是谁" | 用户名由前端自报 = 能把消耗记到别人头上 |
| 查询范围 | 超管看全部，其他人只能看自己 | 这个数字直接对应公司花的钱 |

上报失败**静默**：看板是旁路，不能因为它挂了让用户问不了问题。但前几次失败会打日志，
否则"看板空了"会被误当成"今天没人用"。

### 日预算（默认关闭）

`.env` 里 `LLM_DAILY_BUDGET_TOKENS` 配一个数就生效，超限时下一轮对话返回 429：

```json
{"error": "今日 token 额度已用完（已用 14869 / 上限 1000）...", "code": "budget_exceeded"}
```

这是**事后拦**：第一次请求时本地还没有数，要等上报回来才知道超了。
真正的硬闸门应该在上报接口里拒绝写入，demo 没做到那一步。

### 怎么开

1. 两端 `.env` 填同一个 `INTERNAL_API_KEY`（`python -c "import secrets;print(secrets.token_hex(24))"`）
2. 建表：`sql/seed.sql` 里有 `llm_usage`，已有库单独跑一次建表语句即可
3. 重新登录后台管理系统 —— 菜单是登录时下发的，不重登看不到新菜单

## 已知限制（诚实版）

- **面向演示与教学，不是生产系统**。没有部署脚本、没有容器化、没有 HTTPS 配置。
- 智能体服务是**单进程串行**处理对话（一把全局锁），为了演示时不串话；生产应换成异步 + 会话外部存储（Redis）。
- 会话保存在内存里，**重启即丢**；空闲 30 分钟也会被回收，重新登录等于新会话（历史不跨令牌保留）。
- 没有令牌黑名单，改密码/登出不会让已发出的令牌立刻失效 —— 这是有效期设 12 小时的原因。
- **没有设 `max_tokens` 上限**：输出长度完全由模型自己决定。量到过一次"查 20 个客户"
  答了 975 token，其中大半是把列表又复述了一遍。真要控成本，这里和列表条数都得收。
- **对话历史只增不减，没有压缩/摘要**：长会话的输入 token 会线性上涨（实测第 2 次请求
  已是第 1 次的 2.46 倍）。生产做法是保留最近 N 轮 + 把更早的总结成一段，
  或者只保留工具结果的摘要而不是原文。这块明确没做。
- **日预算只能事后拦**：第一次对话时本地还没有用量数据，会先放过去，
  要等上报回来才知道超了。硬闸门应该在上报接口里做（超限直接拒绝写入）。
- **用量流水不会自动归档**：`llm_usage` 一行一次请求，长期会一直长。
  生产应该定期把 90 天前的明细聚合成天表再删明细，这里没做。
- `sale_order` 接口没有配 `filterset_fields`，`?customer_id=` 之类参数会被忽略并返回全量
  （`customer_tracking` 是支持的）。智能体工具因此改为取回列表后自己比对，不依赖服务端过滤。
- 订单金额是**下单时算好落库**的，之后如果通过 `/api/sale_order_item/` 单独增删明细行，
  订单的 `amount` 不会跟着重算。走正常下单流程没有这个问题；需要改单请走订单接口。
- 没有做工具调用的流式输出，长回答是整段返回的。

### 为什么没有 migrations

建表由 `sql/seed.sql` 负责（17 张 `CREATE TABLE` + 种子数据一次导入），这是这个项目**唯一**的表结构来源。
再加一份 migrations 就是两个真相，长期必然对不上——尤其是 `seed.sql` 里还有索引、注释、排序规则这些
ORM 不描述的东西。要改成迁移驱动，步骤是：

```bash
python manage.py makemigrations system          # 从 models 生成 0001_initial
python manage.py migrate --fake-initial         # 已用 seed.sql 建好表的话，标记为已应用
```

之后 `seed.sql` 只保留 `INSERT`（把 DDL 那半删掉），否则 `migrate` 建完表再导 seed 会撞"表已存在"。

## 关于这份代码的来历

后端 RBAC 脚手架与前端的后台管理模板，都是本仓库作者自己的两个项目：

- `dj-rbac-api` —— Django + DRF + SimpleJWT 的权限系统（`backend/`）
- `vue-rbac` —— Vue 3 + Element Plus 的后台管理（`frontend/`）

本仓库把它们合并到一起，并在上面加了工作台、明暗主题、金额精度治理，
以及完整的智能体接入层（`agent-server/agent/`、`agent-server/crm/`、`bridge.py`）。
三端在同一个仓库里，是为了让"智能体调用业务接口、用同一个身份、受同一套 RBAC 约束"
这件事能被一次跑通。
